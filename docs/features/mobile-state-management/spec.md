# Spec. Mobile State Management

> 한 줄 요약. 홈 화면 내부에 묶인 알림/검색 상태를 테스트 가능한 앱 상태 계층으로 분리한다.

## 배경

현재 알림 목록과 검색 화면 표시 여부는 `HomeScreen` 내부 `StatefulWidget`에 직접 들어 있다. 기능이 늘어나면 로컬 저장, API 연동, 알림 엔진이 모두 화면 상태에 결합될 가능성이 높다.

상태관리 계층을 먼저 두면 UI는 렌더링과 사용자 입력 처리에 집중하고, 알림 추가/수정/삭제 같은 도메인 액션은 독립적으로 테스트할 수 있다.

## 기능 목록

### 알림 상태 provider 분리

알림 목록과 알림 변경 액션을 provider/controller 계층으로 이동한다.

**동작 방식**

- 앱 루트에 provider scope를 추가한다.
- 알림 목록 상태를 provider에서 관리한다.
- 홈/검색/시트는 provider의 상태와 액션을 사용한다.

**포함 범위**

- Riverpod 도입
- 알림 목록 provider/controller
- 추가/수정/삭제 액션 분리
- UI 구독 방식 변경

**제외 범위**

- 서버 API 연동. 별도 기능에서 처리한다.
- 로컬 저장 구현 자체. 저장소 기능과 조합 가능하게 경계만 둔다.

## 입출력

**입력**

- 사용자 액션. 역 선택, 알림 옵션 변경, 삭제 요청.
- 초기 알림 목록. 현재 샘플 데이터 또는 저장소에서 제공되는 목록.

**출력**

- 최신 알림 목록 상태.
- UI에서 구독 가능한 loading/error-free state.

## 제약 조건

- 기존 UI 동작을 유지해야 한다.
- 상태 변경 로직은 widget 없이 단위 테스트 가능해야 한다.
- provider 도입으로 화면 파일이 과도하게 복잡해지면 안 된다.

## 예외 케이스

- 같은 역 알림 추가 → 기존 항목을 새 옵션으로 교체한다.
- 알림 삭제 → 해당 station name 항목만 제거한다.
- 모든 알림 삭제 → 빈 상태 UI를 표시한다.

## 채택 근거

**핵심 이유**

- 이후 로컬 저장/API 연동/알림 엔진을 붙일 때 화면 상태 결합을 줄인다.

**보조 이유**

- Riverpod은 Flutter에서 테스트와 의존성 주입이 단순하다.
- 현재 코드 구조 분리 이후 자연스러운 다음 단계다.

**기각된 대안**

- `setState` 유지. 초기에는 단순하지만 기능 확장 시 결합도가 빠르게 커진다.
- Bloc 도입. 현재 규모에는 보일러플레이트가 크다.

## 비기능 요건

**성능**

- 알림 목록 변경 시 필요한 위젯만 다시 빌드되어야 한다.

**보안**

- 위협 모델. 이 기능은 클라이언트 메모리 상태만 다루며 민감 정보를 추가하지 않는다.
- 상태 로그에 위치나 식별자를 남기지 않는다.

**확장성**

- 로컬 저장소와 원격 API repository를 provider dependency로 교체 가능해야 한다.

## 용어 정의

- **Provider.** UI가 구독하는 상태 또는 의존성 단위.
- **Controller.** 상태 변경 액션을 제공하는 객체.
