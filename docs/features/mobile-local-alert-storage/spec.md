# Spec. Mobile Local Alert Storage

> 한 줄 요약. 사용자가 설정한 지하철 알림을 앱 재시작 후에도 유지한다.

## 배경

현재 Flutter 앱의 알림 목록은 `HomeScreen` 내부 메모리 상태로만 관리된다. 사용자가 알림을 추가하거나 수정해도 앱을 종료하면 초기 샘플 알림 상태로 돌아간다.

알림 앱에서 설정 유지가 되지 않으면 핵심 사용 흐름을 신뢰할 수 없다. 서버 동기화나 계정 기능을 만들기 전이라도, 단일 기기 내 알림 설정은 로컬에 보존되어야 한다.

## 기능 목록

### 로컬 알림 설정 저장

사용자가 추가/수정/삭제한 알림 목록을 로컬 저장소에 기록하고, 앱 시작 시 복원한다.

**동작 방식**

- 앱 시작 시 로컬 저장소에서 저장된 알림 JSON을 읽는다.
- 저장된 데이터가 있으면 `SubwayAlert` 목록으로 복원해 홈 화면에 표시한다.
- 알림 추가/수정/삭제가 발생하면 최신 목록을 다시 저장한다.

**포함 범위**

- `SubwayAlert` 직렬화/역직렬화
- `Station` 참조 복원
- 앱 시작 시 저장된 알림 복원
- 알림 변경 시 저장소 반영

**제외 범위**

- 서버 동기화. 이 기능은 단일 기기 로컬 보존만 다룬다.
- 사용자 계정. 인증 모델이 아직 없다.
- 푸시 알림 실제 발송. 저장된 설정을 실행하는 기능은 별도 기능이다.

## 입출력

**입력**

- 알림 목록. `List<SubwayAlert>`.
- 알림 항목. station name 또는 station id, `push`, `vibration`, `voice`.

**출력**

- 복원된 알림 목록. 유효한 저장 데이터가 없으면 기본 알림 목록 또는 빈 목록.
- 저장 성공/실패 결과. UI는 실패 시 기존 메모리 상태를 유지한다.

## 제약 조건

- Flutter 앱에서 동작해야 한다.
- 저장소는 앱 재시작 후 유지되어야 한다.
- 손상된 저장 데이터가 앱 시작을 막으면 안 된다.

## 예외 케이스

- 저장 데이터가 비어 있음 → 기본 상태로 시작한다.
- 저장 JSON 파싱 실패 → 저장 데이터를 무시하고 기본 상태로 시작한다.
- 저장된 station name을 현재 역 목록에서 찾을 수 없음 → 해당 알림은 건너뛴다.
- 저장 실패 → UI 상태는 유지하고 다음 변경 시 다시 저장을 시도한다.

## 채택 근거

**핵심 이유**

- 알림 설정 유지가 되지 않으면 앱의 핵심 가치가 성립하지 않는다.

**보조 이유**

- 서버/API 연동 전에도 독립적으로 완성 가능한 기능이다.
- 이후 API 동기화의 캐시 계층으로 재사용할 수 있다.

**기각된 대안**

- 서버 저장 우선. 인증과 API 도메인이 필요해 선행 비용이 크다.
- SQLite/Drift 우선. 현재 데이터 구조에는 과하다.

## 비기능 요건

**성능**

- 앱 시작 시 알림 복원은 체감 지연 없이 완료되어야 한다.
- 알림 목록 수십 개 수준에서 직렬화 비용은 무시 가능해야 한다.

**보안**

- 위협 모델. 저장되는 값은 역명과 알림 방식이며 민감 정보는 포함하지 않는다.
- 위치 기록이나 사용자 식별자는 저장하지 않는다.

**확장성**

- 단일 기기 로컬 저장을 가정한다. 서버 동기화가 필요해지면 repository 계층을 유지하고 원격 source를 추가한다.

## 용어 정의

- **로컬 저장소.** 앱 설치 단위로 유지되는 기기 내부 저장 공간.
- **알림 설정.** 사용자가 선택한 역과 푸시/진동/음성 옵션 조합.
