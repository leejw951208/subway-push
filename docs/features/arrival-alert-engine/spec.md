# Spec. Arrival Alert Engine

> 한 줄 요약. 사용자가 설정한 역에 가까워졌을 때 중복 없이 알림을 트리거하는 도착 판정 엔진을 만든다.

## 배경

현재 앱은 역과 알림 방식을 설정할 수 있지만, 실제로 “언제 알릴지”를 판단하는 로직이 없다. 지하철 하차 알림 앱의 핵심은 사용자의 현재 위치 또는 이동 상태를 기준으로 목표 역 도착을 감지하는 것이다.

위치 권한, 역 좌표, 백그라운드 정책은 복잡하므로 첫 단계에서는 테스트 가능한 순수 도메인 엔진으로 도착 판정과 중복 방지 규칙을 분리한다. 이후 네이티브 위치/알림 계층과 연결한다.

## 기능 목록

### 도착 판정 엔진

현재 위치와 목표 역 정보를 입력받아 알림 트리거 여부를 판단한다.

**동작 방식**

- 알림 설정과 현재 위치를 입력받는다.
- 목표 역 좌표와의 거리를 계산한다.
- 거리 임계값 안으로 진입하면 알림 이벤트를 생성한다.
- 이미 알림한 역은 중복 알림하지 않는다.

**포함 범위**

- 현재 위치/역 위치 모델
- 거리 기반 도착 판정
- 중복 알림 방지
- push/vibration/voice 옵션별 이벤트 표현
- 순수 도메인 테스트

**제외 범위**

- 외부 실시간 지하철 API. 도착 판정은 위치 기반으로 시작한다.
- 서버 기반 푸시. 로컬 알림과 연결한다.
- 장시간 백그라운드 위치 정책 최적화. 별도 플랫폼 검토가 필요하다.

## 입출력

**입력**

- 현재 위치. 위도/경도.
- 목표 역 위치. 위도/경도와 station id/name.
- 알림 설정. push/vibration/voice.
- 이미 알림한 상태.

**출력**

- 알림 이벤트. 알림 필요 여부와 실행할 방식 목록.
- 엔진 상태. 중복 방지를 위한 notified station set.

## 제약 조건

- 도메인 로직은 Flutter plugin 없이 테스트 가능해야 한다.
- 거리 계산 기준과 임계값을 명시해야 한다.
- 같은 역에 대해 반복 알림을 방지해야 한다.

## 예외 케이스

- 현재 위치 없음 → 알림 이벤트 없음.
- 역 좌표 없음 → 해당 알림은 판정하지 않음.
- 임계값 밖 → 알림 이벤트 없음.
- 이미 알림 완료 → 추가 이벤트 없음.

## 채택 근거

**핵심 이유**

- 도착 판정은 앱 핵심 로직이므로 UI/플랫폼 코드와 분리해 테스트해야 한다.

**보조 이유**

- 순수 함수/서비스로 만들면 위치 provider와 알림 service를 나중에 쉽게 연결할 수 있다.
- 중복 방지 정책을 명확히 검증할 수 있다.

**기각된 대안**

- UI에서 직접 거리 판정. 테스트와 유지보수가 어렵다.
- 실시간 지하철 API 우선. API 신뢰성/노선별 차이로 초기 범위가 커진다.

## 비기능 요건

**성능**

- 알림 목록 수십 개 기준 위치 업데이트마다 즉시 판정 가능해야 한다.

**보안**

- 위협 모델. 위치 데이터는 민감 정보이며 서버 전송 없이 로컬 판정으로 시작한다.
- 위치 기록을 영구 저장하지 않는다.

**확장성**

- 역 수가 많아지면 근처 역 index 또는 spatial lookup으로 개선한다.

## 용어 정의

- **도착 판정.** 현재 위치가 목표 역 반경 안에 들어왔는지 판단하는 로직.
- **중복 방지.** 한 역에 대해 같은 여정에서 알림을 반복하지 않는 정책.
